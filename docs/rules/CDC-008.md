# CDC-008: Multi-bit value synchronized bit by bit

| Field | Value |
|---|---|
| Default severity | Error |
| Result status | PotentialRisk if the synchronized bits are read together; NeedsReview otherwise. If the clock relation is unknown, it becomes NeedsReview |
| Implemented in | `src/rules/RuleEngine.cpp` (`Cdc008`); facts from `src/cdc/AdvancedAnalysis.cpp` (`checkGray`, `analyzeConvergence`) |
| Tests | `tests/cdc/test_cdc_advanced.cpp` (tag `[CDC-008]`), smoke example (`status[3:0]`), `examples/cdc_advanced` |

## Purpose
When the bits of a multi-bit value pass separate synchronizers, each bit resolves independently. If more than one bit changes in a source cycle, the destination can capture a mix of old and new bits: a value that never existed (data incoherency).

## Applicability
- A multi-bit crossing synchronized by per-bit flop chains (`two-flop`, `three-flop`, `multi-flop`, width > 1), or
- bits of one multi-bit source register synchronized by **separate** single-bit synchronizers into one clock (`splitWith`), for example a `generate` loop of `sync_2ff` instances;

where the source is not recognized as Gray-encoded (a `gray` path is not reported).

Status:
- **PotentialRisk** if one destination register reads two or more of the synchronized bits (`bitsReadTogether`);
- **NeedsReview** if every bit is used on its own inside the design. These may be independent flags, or the bits may be combined outside the design.

## Gray and toggle recognition (why a path is not reported)
A vector of toggle bits (`t <= t ^ {ev1, ev0}`) is a set of independent toggle synchronizers (`toggle`), not a multi-bit value.

The source register's data bits are traced through XOR/XNOR, NOT, constant shifts, and muxes whose other arm is constant, holds the register's value, or has a constant select. The result must be `D[k] = X[k] ^ X[k+1]` and `D[N-1] = X[N-1]` for one binary value `X`. A word-wide mux whose arms are each Gray-encoded, constant or held is also accepted (`g <= drop ? bin2gray(commit) : bin2gray(ptr + 1)`). The binary value is checked for an increment of at most one per clock (an adder or subtractor whose other operand is 0 above bit 0, also through Verilog width extension, or a mux between such a value and a hold). If the register is loaded from more than one binary value, switching between them can change several bits at once. In that case, or when the step cannot be proven, the path stays `gray` with the protocol condition unverified.

## False-positive limits
- Independent single-bit flags packed into one vector are reported as NeedsReview when they are used separately.
- Gray encoders written in a form the tracer does not understand (for example through a lookup table) are reported. The path conditions show why it is not `gray`.

## Test cases
- Positive: a 4-bit bus `s1 <= g; s2 <= s1; y <= s2 + 3` (PotentialRisk); `g[0]` and `g[1]` through separate synchronizers combined in `y` (PotentialRisk, not CDC-005); per-bit synchronizer whose outputs only drive a port (NeedsReview); `status[3:0]` in the smoke example (NeedsReview).
- Negative: Gray-coded pointer; one bit synchronized twice (that is CDC-005).

## Fix
Gray-code counters and pointers before synchronizing them. Transfer other multi-bit values with a handshake or MUX synchronizer (capture under a synchronized qualifier), or through an asynchronous FIFO.

## Waivers
A reviewed hit of this rule can be waived by rule id, path fingerprint, or source/destination name (see [docs/waivers.md](../waivers.md)). A waived hit stays in all reports, marked with its waiver, and no longer counts as a violation.
