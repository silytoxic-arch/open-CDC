## 3. 关键算法

### 3.1 时序依赖图
对每个寄存器输入位，先用 `DesignView::driver` 找到驱动源：
- 驱动源是寄存器、锁存器、输入端口或黑盒时，记为直连源。
- 驱动源是组合单元时，对单元做后序 DFS。按位相关的单元（与、或、异或、非、MUX、DynInsert）按位展开，全相关的单元（算术、比较、移位等）按整个单元展开一次。各输入的源集合按节点合并成位区间：经过 MUX 的 S 端或数组下标时加 `kSelect` 标志，经过非反相器的逻辑时加 `kLogic` 标志。只经过反相器时保留直连属性，并翻转极性标记。

源集合会被驻留去重，存放在一个扁平池中。只有一个直连源的位不进入驻留，直接用 `BitInput` 内联表示。这一点是内存与设计规模成线性关系的关键。

### 3.2 跨域判定与分组
遍历每个已解析时钟的目标寄存器的每个引脚，取每个源节点的时钟集合与目标时钟集合中最"危险"的一对：异步优先于未知；同时钟、同步、互斥都不算跨域；未知关系在 `assume_sync` 策略下也不算。

结果按（源、目标、引脚）聚合成路径，宽度取 max(目标位数, 源位数)。路径重建时，从目标引脚位沿驱动 hops 和单元输入回溯，在每个单元处选第一个能到达源节点的输入，从而得到"源寄存器 → 线网/端口 → 逻辑 → 目标寄存器"的完整步骤。

### 3.3 同步器识别
1. **链**：对每条数据路径的每个目标位向后找下一级。下一级必须同时钟同边沿，数据输入是导线或反相器，直接来自当前级这一位；可以是另一个寄存器，也可以是同一向量寄存器的另一位。最多找 8 级。当前级的其他读者计为扇出问题。读者查询使用"按层批量扫描"的 `SeqGraph::consumersOf`。
2. 所有目标位的最短链长度 ≥2 时，按 2、3、N 级分类，再逐条检查条件：
   - 全部满足、单比特：必要条件已验证。
   - 全部满足、多比特：协议条件未验证，未验证项为"逐位同步要求每次只变一位（Gray），CDC-008"。
   - 有条件不满足：结构已识别。
3. **受同步信号限定的数据**：从目标寄存器的使能锥和数据锥中带 `kSelect` 的源出发做 BFS，可经目标域寄存器追溯 2 级，寻找已识别同步器第 2 级以后的寄存器，并且该同步器的源时钟与数据源时钟相同或同步。
   - 同步复位输入不参与查找。
   - 源触发器 D 端为常量的同步器视为复位桥，也不参与。这条规则来自 verilog-axis 异步 FIFO 中发现的一个误判，见第 4.2 节。
4. 仍未识别、且是导线直接进入目标寄存器的 → 单级同步（`single-flop`）；其余为未同步。

### 3.4 规则判定
| 规则 | 条件 | 严重度 / 状态 |
|---|---|---|
| CDC-001 | 宽度 1，未识别同步器（经组合逻辑，或进入使能/同步复位） | Error / Violation |
| CDC-002 | 宽度 1，单级同步、链长小于 `minSyncStages`，或首级还驱动其他逻辑 | Warning / Violation |
| CDC-003 | 宽度大于 1，未同步或只有单级 | Error / Violation |
| CDC-010 | 时钟关系未知且策略为 `report` | Warning / NeedsReview（同一路径上的其他命中也降为 NeedsReview） |

### 4.1 测试明细
168 个 CTest 测试：160 个 Catch2 用例（本阶段新增 27 个）、6 个 CLI 端到端测试、2 个 GUI 无头测试。

`cdc_rules` 示例的 12 条路径，逐条与设计意图一致：
- CDC-001 ×2、CDC-002 ×2、CDC-003 ×1、CDC-010 ×1；
- 2 级同步器 ×3、3 级同步器 ×1、受限定数据 ×1；
- "首级前有逻辑"的链 ×2，状态为需复核（规则 CDC-004 在阶段 5 实现）。

开发中发现并修复的问题：
1. 向量移位寄存器形式的同步器（`reg [2:0] s; s <= {s[1:0], d}`）没有被识别：链查找不允许在同一个寄存器内前进。这是很常见的写法，已修复并加了测试。
2. 两处临时对象悬垂引用（`RuleRegistry::standard().rules()` 的范围 for），由 GCC 的 `-Wdangling-reference` 发现。
3. 规则消息措辞。

### 4.2 开源工程验证（verilog-axis，31 个模块，无约束）
- 29 个单时钟模块：0 条跨域路径，没有误报。
- `axis_async_fifo`（以及 `_adapter`）：8 条路径，逐条核对源码：
  - 2 条复位桥（2 级）；
  - 2 条格雷码指针（13 位，逐位 2 级，协议条件未验证）；
  - 3 条 toggle 同步器（3 级）；
  - 1 条存储器读（受同步写指针限定）。

  因为没有约束，时钟关系未知，8 条都只报告 CDC-010（需复核）。
- 这次验证发现并修复了一个误判：存储器读路径最初把**复位同步器输出**当成了数据限定信号，而且宽度报成了整个存储器的 40960 位。修复后，限定信号是 `wr_ptr_gray_sync2_reg`（同步后的写指针），宽度为元素宽度 10；另外新增了一个"复位同步器不是限定信号"的测试。

### 4.3 性能
| 设计 | Release | 峰值内存 |
|---|---|---|
| 2 万个实例、6 万个寄存器（192 万位），单时钟 | 2.3 s | 197 MB |
| 5000 对跨域单元（1 万条跨域路径） | 0.26 s | 56 MB |

开发中用 callgrind 定位并解决了两个性能问题：
1. `DesignView` 对同一线网的驱动区间做线性查找。用宽线网数组连接 2 万个实例时这是 O(n²)，Debug 构建耗时 72 s。改为二分查找，并加前缀最大值以正确处理重叠区间。
2. 每个"只有导线连接"的寄存器位都驻留了一个单元素源集合，内存达到 538 MB。改为内联表示、扁平池存储，并在合并源时不再排序，内存降到 234 MB。

## 5. 已知限制

1. Windows/MSVC 仍未实际编译。
2. 没有 `set_input_delay -clock` 的输入端口、锁存器、黑盒，以及时钟未解析的寄存器，都不参与 CDC 检查，只以 `CDC-NO-DOMAIN` 汇总列出。
3. 进入异步复位端的跨域只统计数量，不做检查（`CDC-RESET-DEFERRED`），由阶段 5 的 CDC-006 处理。
4. 同步器首级前有组合逻辑时，路径状态为"需复核"，但目前还没有对应规则，CDC-004 在阶段 5 实现。
5. 逐位同步的多比特值（如格雷码指针）不报告 CDC-003，只标为"协议条件未验证"；格雷码检查（CDC-008）在阶段 5 实现。
6. 限定信号的查找深度有限（目标域内最多 2 级寄存器），更远的限定信号找不到，会被报告为 CDC-003。
7. 源集合按位区间聚合，因此多比特源的"源位数"是区间宽度，不是精确的位集合；这会影响宽度判定，但不影响是否跨域。
8. 扇出只统计寄存器输入，同步器首级直接驱动输出端口的情况不算扇出问题。
9. 准静态信号（如配置寄存器）也会被报告；豁免（waiver）机制在阶段 7 实现，路径已带有稳定指纹，为此预留。

## 6. 下一阶段（阶段 5：高级 CDC 分析）

按总提示词的阶段划分，接下来的工作是：
1. **同步器识别扩展**：toggle、脉冲、请求/应答握手、格雷码（检查源端 `b ^ (b >> 1)` 结构和目标端 gray→bin）、异步 FIFO（存储器 + 双向格雷指针 + 满/空比较）。
2. **规则**：
   - CDC-004：同步链中的组合逻辑；
   - CDC-005：重汇聚（同步器输出前向 BFS 加位集标签）；
   - CDC-006：异步复位释放（复位同步器识别，复位源域与寄存器域比较）；
   - CDC-007：脉冲丢失（源为可能的单周期脉冲且目标为电平同步，结合时钟周期判断）；
   - CDC-008：多比特同步不一致（逐位同步的非格雷值）；
   - CDC-009：组合逻辑毛刺跨域。
3. 每条规则的规格文档，以及正例和反例测试。
